## معماری payload وبلاگ

در build پایه، HTML و `__NUXT_DATA__` به‌ترتیب برای فهرست انگلیسی `209,857 / 140,825`، فهرست فارسی `255,929 / 183,453`، مقالهٔ انگلیسی `253,670 / 163,240` و مقالهٔ فارسی `296,248 / 201,648` بایت بود. query فهرست ردیف کامل می‌خواند و داده را بعد از فیلتر زبان و وضعیت انتشار به Nuxt می‌دهد. جست‌وجو عنوان، توضیح و برچسب را می‌خواند. کارت برای زمان مطالعه AST بدنه را هنگام رندر پیمایش می‌کند. حذف مستقیم `body` زمان مطالعه را صفر می‌کند.

در مقاله، بدنه برای `ContentRenderer`، فهرست مطالب و زمان مطالعه لازم است. دادهٔ ناوبری `path/title` و خروجی ترجمه `path` مصرف می‌کند. فیلتر انتشار و تطبیق slug پیش از استفاده ضروری است. `payloadExtraction: false` داده را در HTML نگه می‌دارد تا دادهٔ قدیمی CDN پاسخ SSR تازه را بازنویسی نکند. کاهش payload اولیه به‌خودی‌خود خواندن دادهٔ Nuxt Content را هنگام پیمایش کلاینت کم نمی‌کند.

در تحلیل شبیه‌سازی‌شدهٔ یک build دیگر از همان SHA، حذف ASTهای بدون مصرف و شماره‌گذاری دوبارهٔ ارجاع‌ها، فهرست EN/FA را به‌ترتیب `134,705 / 175,694` بایت خام و `31,517 / 38,598` بایت Brotli کوچک‌تر کرد. برای دادهٔ ناوبری و ترجمهٔ دو مقاله، با حفظ بدنهٔ جاری، برآورد `144,171 / 177,648` بایت خام و `33,091 / 38,857` بایت Brotli بود. حجم شبکهٔ واقعی و اثر hydration پس از یک تغییر محصول هنوز سنجیده نشده‌اند. HTML فهرست EN بین دو build پایه ۵۰۵ بایت فرق داشت و payload یکسان بود.

## فاصلهٔ آزمایشگاه و Production

در یک جفت نوبتی برای هر زبان، نسخهٔ محلی پایه و Production با همان پروفایل موبایل مقایسه شدند. SHA گزارش‌شدهٔ استقرار Production با SHA پایه یکسان بود. این چهار پروب در میانه‌های A/B وارد نشده‌اند.

- `/blog`، local → Production. LCP مدل‌شده `11,717 → 4,080` ms. LCP مشاهده‌شده `583 → 1,447` ms. TTFB `5 → 427` ms. کل انتقال `2,257,393 → 920,722` بایت. HTML `210,160 → 58,154` و CSS ورودی `605,757 → 53,260` بایت. شروع درخواست تصویر پس از پاسخ سند `207 → 590` ms. انتقال محلی بدون content encoding، و HTML/CSS Production با `br/br` و cache سند `HIT` بود.
- `/fa/blog`، local → Production. LCP مدل‌شده `12,105 → 4,282` ms. LCP مشاهده‌شده `580 → 1,357` ms. TTFB `4 → 455` ms. کل انتقال `2,316,678 → 941,208` بایت. HTML `256,232 → 69,271` و CSS ورودی `605,757 → 53,314` بایت. شروع درخواست تصویر پس از پاسخ سند `180 → 497` ms. انتقال محلی بدون content encoding، و HTML/CSS Production با `br/br` و cache سند `HIT` بود.

فشرده‌سازی و بایت کمتر پاسخ Production مستقیماً دیده شدند. پاسخ محلی از HTTP/1.1 و پاسخ Production از h2 استفاده کرد. مسیر شبکه، CDN و cache هم متفاوت بودند. مرورگر سرد، cache CDN یا مسیر اتصال را کنترل نمی‌کند. در هر دو مسیر، پاسخ سند و LCP خام در loopback زودتر از Production ثبت شدند، در حالی که مدل Lighthouse نتیجهٔ معکوس داد. LCP مدل‌شده زمان مشاهده‌شدهٔ Chrome نیست و پاسخ به اثر شبکه و CPU مدل‌شده حساس است. مقایسهٔ تک‌جفت سهم مستقل فشرده‌سازی، اولویت، connection reuse یا CPU را تعیین نمی‌کند. تاریخی بودن ST-03 نیز اجازهٔ استفاده از آن به‌عنوان کنترل A/B این تغییر را نمی‌دهد.

1. **فهرست وبلاگ.** فیلدهای کارت و عدد زمان مطالعه را در مرحلهٔ تولید یا handler نگه دارید. برآورد `31–39 KB` Brotli برای سند اولیه است. اطمینان به کاهش اندازه بالا و به اثر LCP پایین است. زمان مطالعه، زبان، ترتیب، draft، جست‌وجو، برچسب و hydration را با GET سرد و پیمایش کلاینت بررسی کنید. [query فهرست](../app/pages/blog/index.vue#L64)
2. **ناوبری و ترجمهٔ مقاله.** queryهای کمکی را به فیلدهای لازم محدود کنید و بدنهٔ مقالهٔ جاری را حفظ کنید. برآورد `33–39 KB` Brotli برای دو مقالهٔ نمونه است. اطمینان به کاهش اندازه بالا و به اثر زمان اجرا پایین است. canonical، hreflang دوسویه، slug نامتقارن، ترتیب ناوبری، کلیدهای قبلی و بعدی و ۴۰۴ draft باید بررسی شوند. [query مقاله](../app/pages/blog/%5B...slug%5D.vue#L38)
3. **layout خانه.** در پروب جدا یک بخش استاتیک پایین صفحه مانند Services را با SSR ثابت برای layout تأخیری آزمایش کنید. هزینهٔ style/layout اولیه سقف نظری فرصت است. اثر یک بخش مشخص اندازه‌گیری نشده و اطمینان پایین است. anchor، فوکوس، جابه‌جایی اسکرول، CLS و متن SSR را بررسی کنید. ## بازتولید

1. از SHA پایه و نسخهٔ همین شاخه دو checkout یا پوشهٔ ساخت مستقل روی یک درایو آماده کنید. از lockfile یکسان، `pnpm 9.12.1` و Node `22.14.0` استفاده کنید. در هرکدام `pnpm install --frozen-lockfile` و `pnpm build` را اجرا کنید و هر دو خروجی `.output` را نگه دارید.
2. در PowerShell جداگانه برای هر نسخه `$env:HOST = '127.0.0.1'` و یکی از پورت‌های `3121` و `3122` را در `$env:PORT` قرار دهید و `node .output/server/index.mjs` را اجرا کنید. `NUXT_PUBLIC_LOAD_PLAUSIBLE=no` را برای هر دو تنظیم کنید. برای تست PDF، `PUPPETEER_EXECUTABLE_PATH` را به همان Chrome بدهید.
3. مسیرها را از `routeSummaries` بردارید. جفت‌های هر مسیر و دستگاه را به ترتیب `runs[].order` اجرا کنید. هر فراخوانی Chrome تازه باز می‌کند. گزینهٔ موبایل `--form-factor=mobile` است و برای دسکتاپ آن را با `--preset=desktop` جایگزین کنید.

```powershell
$env:CHROME_PATH = '<absolute path to Chrome 157.0.8103.79>'
$target = 'http://127.0.0.1:3121/blog'
$prefix = '<temporary directory>/before-blog-en-r1'
node '<lighthouse-13.6.0>/cli/index.js' $target --only-categories=performance --throttling-method=simulate --locale=en-US --output=json --output=html --output-path=$prefix '--chrome-flags=--headless=new --disable-extensions --lang=en-US' --save-assets --form-factor=mobile
```

4. در فایل JSON از دستگاه، مسیر و نسخه گروه بسازید. هر ستون را مرتب کنید و مقدار میانی را بخوانید. `delta = afterMedian - beforeMedian` و `percent = 100 × delta / beforeMedian` است. آرایه‌های `fonts` از `measurement.fontColumns` و `fontAssets` استفاده می‌کنند. برای انتقال Roobert جمع بایت سه مسیر `Roobert-*.woff2` را بگیرید.
